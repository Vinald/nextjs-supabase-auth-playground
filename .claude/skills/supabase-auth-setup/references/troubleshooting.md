# Troubleshooting — errors actually hit, and root causes

| Symptom | Root cause | Fix |
|---|---|---|
| Every route 500s as soon as `.env.local` is empty | `createServerClient`/`createBrowserClient` throw synchronously on empty URL/key args, and that throw runs inside the proxy/middleware, which fires on every request | Guard the proxy: skip session refresh if env vars are unset. Guard each page's `createClient()` call in try/catch. |
| `supabase login` fails with `Cannot use automatic login flow inside non-TTY environments` | The CLI's OAuth flow needs a real browser-backed terminal; SSH/agent/non-interactive shells don't have one | Run `supabase login` in a real terminal (opens the browser normally), or use a personal access token via `SUPABASE_ACCESS_TOKEN` — note a PAT is account-wide, not project-scoped, so prefer the terminal route when possible |
| `{"error_code":"phone_provider_disabled"}` from `/auth/v1/otp` even with a Send SMS hook fully deployed and configured | The Phone *provider* toggle and the Send SMS *hook* are two separate settings. The hook only controls how SMS gets sent once phone auth itself is enabled. | Dashboard → Authentication → Sign In / Providers → Phone → enable the toggle. (Menu may be labeled "Providers" in older docs — current dashboards call it "Sign In / Providers".) |
| `{"error_code":"unexpected_failure","msg":"Unexpected status code returned from hook: 500"}` | Supabase Auth's client-facing error wrapper does not forward the hook function's own error body — this message is all you get regardless of what the function actually returned | Bypass Supabase Auth: hand-sign a Standard Webhooks payload and POST it directly to the deployed function URL to see its real JSON error response (see SKILL.md's "Debugging technique" section) |
| Africa's Talking sandbox call returns `HTTP 401 The supplied authentication is invalid`, even with a key that "looks right" | The API key must come from *inside the Sandbox app specifically* (account.africastalking.com/apps/sandbox → Settings → API Key). A key copied from the live/production app looks like the same format (`atsk_...`) but is a different credential and does not work with `username=sandbox`. | Regenerate/copy the key while explicitly viewing the Sandbox app context, not the live app. |
| Same 401 immediately after getting a fresh, correctly-scoped sandbox key | Freshly generated/rotated Africa's Talking keys take roughly 15–20 seconds to propagate before the API accepts them | Wait ~15–20s and retry before concluding the key itself is wrong |
| No `supabase functions logs` command | Removed/not present in CLI 2.113.0 (may differ by version — check `supabase functions --help`) | Use the Supabase dashboard's Edge Functions → Logs tab, or the direct-signed-payload technique to see function-level errors without needing log access at all |
| OAuth (e.g. Google) completes on the provider's side but never redirects back to the app | Two different callback URLs get conflated: the provider's redirect URI (→ Supabase's own `/auth/v1/callback`) vs. Supabase's Redirect URLs allow-list (→ the app's own callback route) | Configure both, separately: provider console gets Supabase's callback URL; Supabase dashboard's Authentication → URL Configuration → Redirect URLs gets the app's own callback route |
| Following an older tutorial that references `middleware.ts` for Supabase session refresh, but the project throws a deprecation error | Next.js 16 renamed `middleware.ts` → `proxy.ts` (and the exported function `middleware` → `proxy`) | Check `next` version in `package.json` before assuming the file name; use `proxy.ts` on Next 16+ |
| Docs/tutorials reference `NEXT_PUBLIC_SUPABASE_ANON_KEY` but the project's actual Supabase dashboard shows a key labeled differently | Newer Supabase projects call the client-safe key the "publishable key" (`sb_publishable_...` format) instead of "anon key" | Check what the dashboard's Settings → API page actually calls it before picking an env var name; same value/slot either way |
